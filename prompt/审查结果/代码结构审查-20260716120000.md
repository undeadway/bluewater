## 一、总体评价

**综合评分：55 / 100（D 级 — 需重大改进）**

Bluewater 作为一个数据库接口适配器，整体架构思路清晰（桥接模式 + 策略模式），但在实现细节和工程化方面存在大量问题。核心的 SQL 模板编译引擎设计合理，但在模块组织、错误处理、测试覆盖、配置管理等方面均存在明显短板。特别是 MySQL 适配器存在**路径引用错误（Broken Reference）**，这是一个会导致运行时崩溃的严重 Bug。

## 三、入口文件职责（`src/index.js`）

| 检查项 | 状态 | 说明 |
|--------|------|------|

| 是否存在 IIFE 副作用 | ❌ | 模块加载时同步读取配置文件 |
| 是否支持多实例 | ❌ | 全局单例，IIFE 中的状态在所有实例间共享 |

### 3.1 问题详述

**1️⃣ IIFE 级别的副作用（严重）**

```js
const [getBwSqlDefs, db, BW_DB_CONFIGS, useCache, DEFAULT_DB_NAME, methodQuery] = (() => {
    // 模块加载时立即执行：
    const database = JSON.parse(readFileSync(process.cwd() + "/res/json/bluewater.json"));
    // 同步 I/O！且路径硬编码！
    archive.init(database.archive);
    // 副作用！
    return [getDef, ...];
})();
```

- ❌ **require 时即执行同步文件 I/O**
- ❌ 如果 `bluewater.json` 不存在，整个模块无法加载
- ❌ 路径固定为 `process.cwd() + "/res/json/"`，无法被调用方自定义

**2️⃣ 引用损坏配置路径（严重）**

`src/index.js` 第 42 行读取 `process.cwd() + "/res/json/bluewater.json"`，但：

```
res/json/ 实际内容：
  bluewater.mysql.json   ← 存在
  bluewater.pg.json      ← 存在
  bluewater.sqlite.json  ← 存在
  funcs_map.json         ← 存在
  sql.json               ← 存在
  bluewater.json         ← 不存在！！！
```

**这会在运行时抛出 `ENOENT` 错误，导致应用崩溃。**

**3️⃣ 回调参数命名不一致**

| 位置 | 参数名 |
|------|--------|
| `query()` 回调 | `success`, `fail` |
| `transaction()` 回调 | `success`, `failed` |
| 注释中的示例 | `success`, `fail` |

- `fail` vs `failed` 混用，调用方容易混淆。

## 六、适配器 / 插件机制

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 是否有契约定义 | ❌ | 无 JSDoc 类型定义 |
| 新增适配器是否需修改入口 | ✅ | 自动发现，添加文件即可 |
| 是否支持运行时切换 | ✅ | 通过 `bluewater(dbName)` 参数切换 |
| 适配器间代码重复率 | ⚠️ | 中等 |

### 6.1 加分项

**✅ 工厂函数模式设计优雅**

```js
// src/adapter/base/index.js
module.exports = (getPrepareMark) => {
    const engine = {
        compire: (input, sqlArgs) => compile(input, sqlArgs, getPrepareMark),
        getRecordsList
    };
    return { compire, getRecordsList, putCache, getCache, ... };
};
```

各适配器只需传入占位符生成函数：
```js
// PostgreSQL:  return `$${paras.length}`  →  $1, $2, $3...
// MySQL:       return `$${paras.length}`  →  $1, $2, $3...
// SQLite3:     return "?"                 →  ?, ?, ?...
```

**✅ 动态适配器发现**

```js
// index.js IIFE 中:
db: (dbName) => require(`./adapter/${dbName}`)
```

新增适配器只需在 `adapter/` 下添加文件，入口自动发现，无需修改入口代码。

**✅ SQL 编译引擎设计合理**

`engine.js` 支持三种标签：
- `#[param]` — 参数占位符（编译为 `$1`、`?` 等）
- `?[condition]` — 条件片段替换
- `![like]` — LIKE 模糊匹配
- `&[function]` — 函数映射

### 6.2 扣分项与改进建议

**❌ MySQL 适配器路径错误（严重 — 运行时崩溃）**

```js
// mysql.js:6
const connection = require("./parts/connection");  // 路径不存在！
// mysql.js:21
const db = require("./parts/base")((paras) => { ... });  // 路径不存在！
```

当前目录结构为 `src/adapter/base/`，而 mysql.js 引用的却是 `./parts/`。这会导致：

```
Error: Cannot find module './parts/connection'
```

> **🔧 改进建议**：将 `./parts/` 改为 `./base/`：
> ```js
> const connection = require("./base/connection");
> const db = require("./base")((paras) => { ... });
> ```

**❌ SQLite3 适配器未使用基类工厂**

相比于 PostgreSQL 和 MySQL（均使用 `base/index.js` 工厂），SQLite3 完全自行实现了全套方法，导致：

1. 缓存逻辑缺失 — SQLite3 没有 `putCache/getCache/clearCache` 方法
2. 代码重复 — `statement()` 实现与 `base/connection.js` 的 `statement()` 高度重叠
3. 连接对象接口不一致 — 返回的 conn 对象是手写的，而非通过工厂生成

> **🔧 改进建议**：让 SQLite3 适配器也使用 `base/index.js` 工厂，仅在 `connect()` 方法和 `prepare()` 中自定义 SQLite3 特有的实现。

**❌ 无适配器接口契约**

当前没有任何 JSDoc 或 TypeScript 类型定义来规范适配器必须实现的方法。

> **🔧 改进建议**：在 `adapter/base/index.js` 中添加 JSDoc 接口契约：
> ```js
> /**
>  * @typedef {Object} DatabaseAdapter
>  * @property {Function} connect - 创建数据库连接
>  * @property {Function} compire - 编译 SQL 模板
>  * @property {Function} getRecordsList - 格式化结果集
>  * @property {Function} getDBSize - 获取数据库大小
>  * @property {Function} getDatabaseInfo - 获取数据库信息
>  */
> ```

## 九、错误处理体系

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 是否使用统一错误类型 | ❌ | 全部使用通用 `Error` |
| 能否精确捕获不同类型错误 | ❌ | 无法区分"参数错误"与"数据库连接错误" |
| 异步错误是否被处理 | ⚠️ | 大部分有 try/catch，但仍有遗漏 |
| 回调参数命名是否一致 | ❌ | `fail` vs `failed` 混用 |

### 9.1 问题详述

**1️⃣ 错误类型扁平化**

```js
function sqlError(msg) {
    throw new Error(msg || "SQL 错误");
}
```

`sqlError` 在 `index.js` 和 `utils.js` 中分别定义，且均抛出通用 `Error`。调用方无法区分：
- SQL 语法错误
- 参数缺失错误
- 不支持的 method 错误
- 数据库连接错误

> **🔧 改进建议**：定义错误类型层次：
> ```js
> class BwError extends Error { constructor(msg) { super(msg); this.name = "BwError"; } }
> class BwSqlError extends BwError {}
> class BwParamError extends BwError {}
> class BwConnectionError extends BwError {}
> ```

**2️⃣ 回调参数 `fail` vs `failed` 不一致**

| 方法 | 失败回调参数 |
|------|-------------|
| `query()` 参数 | `fail` |
| `transaction()` 参数 | `failed` |
| `execute()` 参数 | `failed` |

## 十一、全局状态与副作用

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 模块加载时副作用 | ❌ | 同步读文件 + 初始化 |
| 依赖 Monkey-patch | ❌ | 严重依赖 `coralian` |
| 多实例状态干扰 | ❌ | 三个实例共享相同状态 |

### 11.1 问题详述

**1️⃣ `select-cache.js` 使用全局 `this` 上下文**

```js
let map = new Map();
this.put = function (sql, param, records, timeout) { ... }  // this 是全局对象！
this.get = function (sql, param) { ... }
```

这不是在类中定义方法，而是在模块顶层使用 `this`，实际绑定到 `module.exports`，但 `let map` 是模块级变量。所有 `bluewater()` 实例共享同一个 `map`，导致**缓存状态全局共享**。

**2️⃣ `sqlite3.js` 使用模块级变量**

```js
let fileName = null;  // 模块级变量！
function connect({ url }) {
    fileName = url;  // 不同实例互相覆盖！
}
```

多实例场景下，后创建的连接会覆盖先创建的 `fileName`，导致 `getDBSize()` 返回错误的文件大小。

## 十二、核心运作逻辑分析

### 12.1 执行流程

```
bluewater(dbName)
  ├─ db(dbName).connect(config)      → 创建适配器连接
  ├─ bwObj.query(arg)
  │   └─ queryFunction(args, conn)
  │       ├─ getBwSqlDefs(dbName)    → 读取 sql-{dbName}.json
  │       ├─ db.compire(sql, args)   → 编译 SQL 模板
  │       ├─ conn.prepare(sql)       → 创建 PreparedStatement
  │       ├─ 检查缓存（select 时）
  │       ├─ stmt[method](params)    → 执行数据库操作
  │       ├─ db.getRecordsList()     → 格式化结果（下划线→驼峰）
  │       └─ conn.tidyUp()           → 适配器后处理
  └─ bwObj.transaction(queue)
      ├─ conn.begin()
      ├─ 依次执行 queue 中的 SQL
      ├─ conn.commit() / rollback()
      └─ closeConn()
```

### 12.2 合理性评价

| 环节 | 评价 | 说明 |
|------|------|------|
| SQL 模板编译 | ✅ 合理 | `#[param]` → `$1`/`?` 的转换干净利落 |
| 条件片段替换 | ✅ 合理 | `?[condition]` 的按需替换 |
| 参数分离 | ✅ 合理 | SQL 与参数分离，防注入 |
| 缓存机制 | ⚠️ 待改进 | 算法设计合理但实现上有全局状态问题 |
| 事务管理 | ✅ 合理 | begin → execute → commit/rollback 流程清晰 |
| 方法绑定 | ⚠️ 风险 | 通过 `for...in` 动态绑定方法到 bwObj |
