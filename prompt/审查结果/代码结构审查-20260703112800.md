## 1. 总体评价

Bluewater 是一个面向 Node.js 环境的数据库中间件适配器，设计理念清晰——**"一次编写 SQL，多数据库运行"**。其核心定位类似于 Java 生态中的 MyBatis 或 Apache DBUtils，旨在为上层应用提供统一的数据库操作接口，屏蔽底层 PostgreSQL、SQLite 等数据库驱动的语法差异。

**总体结论**: 项目思路可取，代码量精简（核心源码约 700+ 行），核心编译引擎设计有亮点。但代码质量处于**原型/实验阶段**，存在大量运行时风险、未完成的 TODO、全局状态污染和缺少错误边界处理。距离生产可用仍有较大差距。

## 2. 架构合理性分析

### 2.1 整体分层架构

```
┌─────────────────────────────────────────┐
│             上层应用 / User App           │
├─────────────────────────────────────────┤
│              bluewater 入口              │
│            src/index.js                  │
├────────────────┬────────────────────────┤
│   SQL 编译引擎  │   Lambda 查询构建器    │
│  parts/base.js  │  components/lambda.js │
├────────────────┴────────────────────────┤
│          适配器层 (Adapter)              │
│  ┌───────────┐  ┌───────────┐           │
│  │ postgres  │  │  sqlite3  │           │
│  └─────┬─────┘  └─────┬─────┘           │
│  ┌─────┴──────────────┴─────┐           │
│  │   parts/connection.js    │           │
│  └──────────────────────────┘           │
├─────────────────────────────────────────┤
│           util 工具层                    │
│  select-cache.js / utils.js / archive.js │
└─────────────────────────────────────────┘
```

### 2.2 优点

- **关注点分离清晰**: 入口 → SQL 编译 → 适配器 → 连接管理 → 工具函数，各层职责明确。
- **适配器模式应用得当**: 通过 `require(\`./adapter/${dbName}\`)` 动态加载驱动，新增数据库只需添加适配器文件。
- **SQL 模板引擎内建**: 使用 `#[param]`、`?[condition]`、`![like]`、`&[function]` 四种标签的自定义模板语法，功能完备。
- **缓存层设计有层次**: select-cache 实现了"内存 → 文件 → 不缓存"三级策略的思路。

### 2.3 架构缺陷

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **配置硬编码路径** | 🔴 高 | `res/json/sql.json` 和 `res/json/bluewater.json` 使用 `process.cwd() + "/res/json/"` 硬编码，无法通过参数自定义，限制了库的可嵌入性 |
| **单例全局状态** | 🔴 高 | `bluewater.json` 在模块加载时即解析（IIFE），所有实例共享同一个 `BW_SQL_DEFS`、`db`、`dbConnConfig`，**无法同时连接多个不同数据库** |
| **缺少 IoC/DI 机制** | 🟡 中 | 适配器通过 `require` 硬加载，没有注册/发现机制，无法在运行时切换或注入 mock 驱动用于测试 |
| **异常处理不统一** | 🟡 中 | 有的地方 throw Error（`sqlError`），有的地方返回 `null`，有的地方吞掉异常后调用回调 |
| **文件命名不一致** | 🟢 低 | `lamdba.js` 应为 `lambda.js`，`sqlite3.js` 在 review 文档中写为 `sqlite.js` |
| **无 TypeScript 类型定义** | 🟢 低 | 纯 JS 项目，对于库项目来说缺少类型定义文件（.d.ts）会降低可维护性 |

## 3. 核心运作逻辑分析

### 3.1 SQL 编译引擎 (`parts/base.js`)

这是本项目**最大的亮点**。

#### 工作流程

```
输入: "SELECT * FROM T WHERE A = #[a] AND B LIKE ![%test%] &[orderBy]"
                    │
                    ▼
     1. &[function] → 函数映射替换 (funcs_map.json)
        → "SELECT * FROM T WHERE A = #[a] AND B LIKE ![%test%]  ORDER BY "
                    │
                    ▼
     2. ?[condition] → 条件判断替换（有条件则替换为 SQL 片段，无条件则为空）
                    │
                    ▼
     3. ![...] → LIKE 标签处理（含通配符替换）
                    │
                    ▼
     4. #[param] → 参数提取 + 占位符替换
        → SELECT * FROM T WHERE A = $1 AND B LIKE $2  ORDER BY $3
        → params: [value_a, "%test%", "column1 DESC"]
                    │
                    ▼
     输出: [compiledSQL, paramsArray]
```

#### 合理性评价

- **编译与执行分离**: `compire`（原文拼写有误，应为 `compile`）只做 SQL 编译，不关心执行，设计合理。
- **参数注入防 SQL 注入**: 通过占位符 `${getPrepareMark(para)}` 而非字符串拼接，依赖底层驱动做参数化查询，方向正确。
- **标签语法丰富**: 四种标签覆盖了参数绑定、条件片段、模糊匹配、函数映射等常见需求。
- **数组参数展开**: `#[param]` 遇到数组时自动展开为 `$1, $2, $3`，实现 IN 子句支持。

#### 潜在问题

1. **拼写错误**: `compire` 应为 `compile`，`getRerord` 应为 `getRecord`，`BW_LIKE_REGX` 应为 `BW_LIKE_REGEX`。
2. **条件替换的 `inputReplace` 函数**: 第二参数命名为 `paras` 但实际来自 `sqlArgs.condition`，变量命名混乱，可读性差。
3. **标签处理顺序**: `&[function]` → `?[condition]` → `![like]` → `#[param]`，但代码中 `compire` 函数里是先调用 `inputReplace`（处理 `?[condition]`）再调用 `compireObjectToArrray`（处理 `#[param]`、`![like]`、`&[function]`），逻辑上条件替换应该最先做，目前是正确的。但 `compireObjectToArrray` 内部先处理 `&[function]` 再 `#[param]` 再 `![like]`，这个顺序合理（函数映射可能生成新标签）。
4. **驼峰转换副作用**: `getRerord` 中的下划线转驼峰逻辑在**每次 select 查询结果**上执行，这是一个有争议的设计——数据库列名映射应该可配置而非强制。

### 3.2 连接管理 (`parts/connection.js`)

- **设计简洁**: 提供 `begin/commit/rollback/prepare/close` 标准接口。
- **延迟连接**: `connect()` 在首次操作时调用，实现 lazy connect，点赞。
- **问题**: `close` 方法没有返回 Promise，但 `index.js` 中 `closeConn` 使用了 `await`，存在隐式类型不匹配。

### 3.3 Lambda 查询构建器 (`components/lambda.js`)

- **链式调用 API**: `bluewater.lambda("table").equal("id", 1).select(["name"])` 语法流畅，API 设计类似 Knex.js。
- **功能覆盖**: WHERE、HAVING、GROUP BY、ORDER BY、LIMIT、OFFSET、DISTINCT、LIKE、BETWEEN 等常用子句均已支持。
- **问题**: 仅支持单表查询，复杂 JOIN 场景完全无法处理；`limit` 方法的 SQL 生成有 bug（见扣分项）。

### 3.4 缓存模块 (`util/select-cache.js`)

- **HashMap 结构**: 两层 Map，外层 key = SQL 的 MD5，内层 key = 参数的 MD5。设计思路合理。
- **过期机制**: 支持 `timeout < 0` 永不过期、`timeout = 0` 立即过期、`timeout > 0` 按毫秒过期。
- **问题**: 
  - 使用 `this.put/this.get` 而没有导出为模块对象，实际上 `this` 指向的是模块的 `exports` 对象，虽能工作但不规范。
  - `map.remove` 和 `typeIs(param, "object")` 等方法不存在，会运行时崩溃。
  - `size()` 返回的是 Map 条目数而非缓存记录数，命名有误导性。
  - `archive` 方法为空实现。

### 3.5 事务处理 (`index.js`)

- `transaction` 方法实现了经典的两阶段事务：先 `begin`，逐条执行，全部成功则 `commit`，任意失败则 `rollback`。
- `execute` 方法实现了无事务的批量执行。
- 问题：`transaction` 和 `execute` 中对于 `item.success` 回调的处理逻辑几乎完全重复，违反 DRY 原则。

## 4. 插件/适配器机制分析

### 4.1 适配器加载机制

```javascript
// src/index.js
const db = require(`./adapter/${dbName}`);
```

这是最简单的"按名加载"模式。适配器只需要：
1. 实现 `connect(config)` 方法，返回连接对象
2. 连接对象需要提供 `begin/commit/rollback/prepare/close` 等方法
3. prepare 返回的 statement 需要提供 `select/insert/update/delete` 等方法

### 4.2 PostgreSQL 适配器 (`adapter/postgres.js`)

| 方面 | 评价 |
|------|------|
| 配置支持 | 完整，支持 Client/Pool/Result 三种模式，支持 SSL、超时、连接池参数 |
| 连接管理 | 通过 `connection(db)` 包装为统一接口，正确调用 `conn.connect()` |
| 参数占位符 | 返回 `$1`, `$2`, ... 与 node-postgres 兼容 |
| Proxy 导出 | 使用 `new Proxy` 统一导出，增加了一层无意义开销 |
| 空方法 | `getDBSize()` 返回 0，`getDatabaseInfo()` 空实现 |

### 4.3 SQLite 适配器 (`adapter/sqlite3.js`)

| 方面 | 评价 |
|------|------|
| 配置支持 | 仅支持 `url` 参数，功能有限 |
| 事务语句 | `BEGIN IMMEDIATE TRANSACTION` 使用了可配置级别，细节到位 |
| 代码质量问题 | ⚠️ `close()` 中有严重 bug：`if (!conn)` 时返回 Promise，但 `conn.finalize()` — 当 conn 为 null 时调用 `finalize()` 会抛异常；反之 `if (conn)` 时什么也不做，不释放连接 |
| 重复代码 | `update/insert/delete` 三个方法完全相同的实现 |
| 文件统计 | `getDBSize()` 使用 `fs.statSync` — 同步阻塞操作不推荐 |

### 4.4 适配器机制评价

| 维度 | 评分 | 说明 |
|------|------|------|
| **扩展性** | ⭐⭐⭐ | 新增适配器只需新建文件并实现接口，门槛低 |
| **接口一致性** | ⭐⭐⭐⭐ | 各适配器对外暴露的接口高度一致 |
| **测试性** | ⭐ | 没有 mock/stub 机制，没有针对适配器的单元测试 |
| **类型安全** | ⭐ | 无接口定义/类型检查，适配器实现错误只能在运行时暴露 |
| **依赖注入** | ⭐ | 硬编码 require，无法在运行时替换适配器 |

**总体**: 适配器机制简单有效，但缺少契约定义（接口/抽象类）和运行时校验，属于"约定大于配置"的轻量方案。与 MyBatis 的 `DataSource` 抽象或 Sequelize 的 `Dialect` 体系相比，差距明显。

## 5. 加分项

### ⭐ 自定义 SQL 模板语法
`#[param]`、`?[condition]`、`![like]`、`&[function]` 四种标签的设计富有创造力，尤其是 `?[condition]` 的条件片段替换实现了类似 MyBatis `<if>` 标签的"动态 SQL"能力，而无需引入 XML 配置。

### ⭐ 三级缓存架构理念
缓存模块中"热数据→内存、温数据→文件、冷数据→不缓存"的设计思路有前瞻性，虽然实现未完成，但设计文档清晰地表达了意图。

### ⭐ Lambda 链式调用 API
在 v0.0.30 这样一个早期版本中就提供了流畅的链式 API，思路领先于很多同类库。设计上与 Knex.js 的 query builder 概念一致。

### ⭐ 事务嵌套的自动合并
`transaction` 方法中对多条 SQL 返回值按 `alias` 自动合并（单条→对象，多条→数组），细节设计周到。

### ⭐ 延迟连接（Lazy Connect）
`connection.js` 中的 `connect()` 延迟调用避免了一创建连接对象就建立物理连接，对连接池场景友好。

### ⭐ 记录集列名驼峰化
自动将数据库返回的 `snake_case` 列名转为 `camelCase`，对齐前端 JavaScript 编码规范。

## 6. 扣分项与改进建议

### ❌ 严重缺陷

#### 6.1 `close()` 逻辑反转（SQLite 适配器）

**文件**: `src/adapter/sqlite3.js`  
**代码**:
```javascript
function close() {
    if (!conn) {          // ← 当 conn 为 null 时才执行释放
        return new Promise((resolve, reject) => {
            conn.finalize();  // ← conn 是 null，这里会抛 TypeError
            ...
        });
    }
    // ← 当 conn 不为 null 时什么也不做，连接泄漏
}
```

**影响**: 🔴 **致命** — 每次数据库操作后连接都不会正确关闭，导致连接泄漏。

**建议**: 改为 `if (conn) { conn.finalize(); conn = null; }`

#### 6.2 `index.js` 中使用未定义的全局对象

**文件**: `src/index.js`  
多处使用 `Coralian.logger`、`String.trim`、`String.contains`、`String.BLANK`、`Array.has`、`typeIs`、`Object.forEach`、`Function.EMPTY_BODY`、`Array.last` 等**非标准方法**。

**影响**: 🔴 **致命** — 这些方法依赖于 `coralian` 包对原生对象的 monkey-patch（原型污染）。如果 `coralian` 版本变化或加载顺序不对，整个项目全部崩溃。

**建议**: 
- 立即停止对原生对象的修改依赖
- 所有工具方法改为显式导入（如 `import { trim, contains } from './util/string-utils'`）
- 考虑移除对 `coralian` 的强依赖

#### 6.3 配置和 SQL 定义的文件路径硬编码

**文件**: `src/index.js`
```javascript
const def = existsSync(process.cwd() + "/res/json/sql.json") ? ...
const database = JSON.parse(readFileSync(process.cwd() + "/res/json/bluewater.json"), ...)
```

**影响**: 🔴 作为 npm 包，使用者**必须**将配置文件放在项目根目录的 `res/json/` 下，无法自定义路径，也无法在 monorepo 或多环境部署中使用。

**建议**: 支持通过环境变量、构造函数参数或链式 API 传入配置路径：
```javascript
const db = bluewater({ configPath: "./config/db.json" });
```

#### 6.4 modules 的 IIFE 加载导致全局单例

**文件**: `src/index.js`  
整个模块初始化在 IIFE 中完成：

```javascript
const [BW_SQL_DEFS, db, dbConnConfig, useCache, dbName, methodQuery] = (() => {
    // 读取配置文件、初始化 archive、加载适配器...
})();
```

**影响**: 🔴 无法创建两个指向不同数据库的 `bluewater()` 实例。在同一进程中连接多个数据库（例如读写分离）完全不可行。

**建议**: 将配置读取延迟到 `bluewater()` 构造函数中，支持传入配置对象：

```javascript
function bluewater(config) {
    const dbConfig = config || loadDefaultConfig();
    // ...
}
```

### ❌ 中等问题

#### 6.5 `select-cache.js` 中使用非标准方法

**文件**: `src/util/select-cache.js`
```javascript
this.remove = function (sql, param) {
    let hash = md5(sql);
    if (!param) {
        return map.remove(hash);  // ← Map 没有 remove 方法
    } else {
        ...
        let obj = map.get(hash);
        if (!obj) return null;
        let result = obj[key];
        delete obj[key];
        ...
    }
}
```

以及：
```javascript
this.has = function (sql, param) {
    if (typeIs(param, "object")) {  // ← typeIs 未定义
        param = JSON.stringify(param);
    }
    let records = map.get(hash, param);  // ← Map.get 只接受一个参数
    return records !== null;
}
```

**影响**: 🟡 `remove()` 和 `has()` 方法在调用时会直接崩溃。

**建议**: 
```javascript
// 标准 Map API
this.remove = function(sql, param) {
    const hash = md5(sql);
    if (!param) return map.delete(hash);
    // ...
};
this.has = function(sql, param) {
    const hash = md5(sql);
    const key = md5(JSON.stringify(param));
    const obj = map.get(hash);
    return !!obj && !!obj[key];
};
```

#### 6.6 Lambda 的 LIMIT 子句 SQL 生成错误

**文件**: `src/components/lambda.js`
```javascript
limit: (from, cnt) => {
    exts.push(`LIMIT #[limitFrom] `);
    paras.limitFrom = from;
    if (cnt) {
        exts.push(`LIMIT #[limitTo] `);  // ← 应使用 OFFSET，而不是再一个 LIMIT
        paras.limitTo = cnt;
    }
    return lambda;
},
```

**影响**: 🟡 当调用 `limit(10, 20)` 时生成的 SQL 为 `LIMIT $1 LIMIT $2`，正确应为 `LIMIT $1 OFFSET $2`。

**建议**: 
```javascript
limit: (from, cnt) => {
    exts.push(`LIMIT #[limitFrom] `);
    paras.limitFrom = from;
    if (cnt !== undefined && cnt !== null) {
        exts.push(`OFFSET #[limitTo] `);
        paras.limitTo = cnt;
    }
    return lambda;
},
```

#### 6.7 Lambda 的 INSERT 实现有安全隐患

**文件**: `src/components/lambda.js`
```javascript
insert: (datas, callback) => {
    // ...
    let inserts = datas.map(data => {
        for (key in data) {
            let value = TypeMap.format(obj.value, obj.type);
            insertData.push(value);
        }
    });
    sql.push("(" + columns.join() + ")");
    sql.push("VALUES");
    sql.push(inserts.join());  // ← 直接拼接值到 SQL 中，而非使用占位符
```

**影响**: 🟡 **SQL 注入风险** — 值被直接拼接到 SQL 字符串中，而非通过 `#[param]` 占位符走预编译路径。

**建议**: Lambda INSERT 应该像其他操作一样使用参数化查询，而非值内联。

#### 6.8 归档模块 (`util/archive.js`) 为空实现

**文件**: `src/util/archive.js` — 只有 `init` 空方法。  
**文件**: `src/components/archive.js` — 只有 `init` 空方法。

**影响**: 🟡 配置中的 archive 功能实际不可用，但代码中（`index.js`）已经调用了 `archive.init(database.archive)`。如果用户配置了 archive，不会有任何效果但也不会有错误提示。

**建议**: 要么实现归档功能，要么去除归档配置项并在 init 中给出警告日志。

#### 6.9 SQL 定义中 method 字段错误

**文件**: `res/json/sql.json`
```json
{
    "editByA": { "method": "insert", "sql": "UPDATE TEST SET ..." },
    "delByA": { "method": "insert", "sql": "DELETE FROM TEST WHERE ..." }
}
```

**影响**: 🟡 `editByA` 是 UPDATE 操作但 method 写成了 `insert`，`delByA` 是 DELETE 操作也写成了 `insert`。虽然实际执行由 statement 对应的方法完成（`stmt.insert`、`stmt.update` 在 postgres 和 sqlite 中实现相同），但这会造成：1) 日志中记录的操作类型错误；2) 缓存策略异常（select 走缓存，非 select 清缓存）；3) 维护混淆。

**建议**: 严格匹配 method 定义与实际 SQL 操作：
```json
{
    "editByA": { "method": "update", "sql": "UPDATE ..." },
    "delByA": { "method": "delete", "sql": "DELETE ..." }
}
```

#### 6.10 `bluewater.json` 与代码中的字段名不一致

**文件**: `src/index.js` 中读取 `database["use-cache"]`，但配置文件中写的是 `"use-cache"`，而 README 中写的却是 `"cache"`。`database["database-name"]` vs README 中的 `"database-name"` 一致但参数名中混合了连字符和下划线风格。

**建议**: 统一命名风格，推荐全小写驼峰（`useCache`、`databaseName`、`methodQuery`），并在代码中做兼容处理。

### ❌ 轻微问题

#### 6.11 拼写错误
- `compire` → `compile`（`base.js`、`index.js`）
- `getRerord` → `getRecord`（`base.js`）
- `REGX` → `REGEX`（`base.js`，多处）
- `lamdba.js` → `lambda.js`（文件名）
- `timtout` → `timeout`（`index.js` 第 76 行）
- `VACCUM` → `VACUUM`（`sqlite3.js`）

#### 6.12 `package.json` 中 scripts 配置错误
```json
"build": " test/index.js"
```
这不是一个有效的 build 命令，应该类似 `node test/index.js`。

#### 6.13 没有单元测试
`test/index.js` 只是一个执行脚本，没有断言、没有测试框架。作为数据库中间件，缺少单元测试和集成测试是严重风险。

#### 6.14 错误回调参数名不一致
`index.js` 的 `runQueryFunction` 中，回调参数名定义为 `failed`：
```javascript
if (arg.failed) { arg.fail(); }  // ← 定义了 failed 却调用 fail
```
但调用时传的是 `fail`：
```javascript
db.query({ name: "...", fail: (err) => { ... } });
```
这会导致错误回调中的 `arg.fail()` 访问的是未定义值（`arg.fail` 而非 `arg.failed`），从而静默失败。

### 8.3 详细分析

#### S1. `components/archive.js` — 死文件

**证据**:
```bash
# grep 全项目，均无匹配
require.*components/archive  → 0 结果
```

`src/index.js` 引用的是 `./util/archive`，而非 `./components/archive`。  
`components/archive.js` 是彻底的 dead code。

**影响**: 🟡 增加认知负担，维护者会困惑"到底哪个 archive 在用？"

**建议**: 删除 `src/components/archive.js`。

---

#### S2. `adapter/parts/` 命名不当

当前路径:
```
adapter/parts/
├── base.js        ← 实际是 SQL 编译引擎 + 缓存操作 + 结果集处理（≈ 适配器基类）
└── connection.js  ← 连接抽象层
```

问题:
- "parts" 是一个占位词，不能表达目录内容的性质
- `base.js` 包含了本项目最核心的 **SQL 编译引擎**、记录转换、缓存操作等多个职责，全部塞在一个文件中
- 作为适配器的"基类"，它被 `postgres.js` 和 `sqlite3.js` 通过 `require("./parts/base")(...)` 调用，路径语义是"从 parts 中拿个东西"，而不是"继承基类"

**建议**:
```
adapter/base/
├── engine.js       ← SQL 编译引擎（当前 base.js 的 SQL 编译部分）
├── connection.js   ← 连接抽象层
└── index.js        ← 导出工厂函数（当前 base.js 的 module.exports）
```

---

#### S3. `index.js` 职责过重

`src/index.js` ~290 行，承担了 **6 项不同职责**：

| 职责 | 行号范围 | 应归属 |
|------|---------|--------|
| 读取 `sql.json` | IIFE 内 | `loader/config-loader.js` |
| 读取 `bluewater.json` | IIFE 内 | `loader/config-loader.js` |
| 初始化 archive | IIFE 内 | 归档模块自身 |
| 动态加载适配器 | IIFE 内 | `adapter/index.js` |
| SQL 执行引擎（`queryFunction`） | ~60 行函数 | `core/executor.js` |
| 事务管理（`transaction`） | `bwObj.transaction` | `core/transaction.js` |
| 批量执行（`execute`） | `bwObj.execute` | `core/executor.js` |
| 方法绑定（`method-query`） | 底部循环 | 可留在入口 |
| Lambda 挂载 | 最后一行 | 可留在入口 |

**建议拆分后的结构**:
```
src/
├── index.js               ← 仅做组装、导出、方法绑定
├── core/
│   ├── executor.js        ← SQL 执行引擎
│   └── transaction.js     ← 事务管理
├── loader/
│   └── config-loader.js   ← 配置加载
├── adapter/
│   ├── base/
│   │   ├── engine.js      ← SQL 编译引擎
│   │   ├── connection.js  ← 连接抽象
│   │   └── index.js       ← 基类工厂
│   ├── postgres.js
│   └── sqlite3.js
├── components/
│   ├── lambda.js          ← Query Builder
│   └── archive.js         ← 归档（待实现）
└── util/
    ├── select-cache.js
    └── utils.js
```

#### S4. `res/json/` 作为 npm 包结构不合理

```javascript
// src/index.js
const def = existsSync(process.cwd() + "/res/json/sql.json") ? ...
const database = JSON.parse(readFileSync(process.cwd() + "/res/json/bluewater.json"), ...)
```

**三个问题**:
1. **`process.cwd()` 不可靠** — 取决于启动目录，在 monorepo、测试框架、工具链中可能与期望不符
2. **路径硬编码不可自定义** — 使用者无法将配置放在自己习惯的位置
3. **`res/` 不是 npm 包的常规目录** — npm 包通常将资源放在 `src/config/` 或 `assets/`，或用 `package.json` 的 `exports` 字段暴露

**建议**:
```javascript
// 方式一：构造函数注入（推荐）
function bluewater(config) {
    const sqlDefs = config.sqlDefs || loadDefaultSqlDefs();
    const dbConfig = config.database || loadDefaultDbConfig();
    // ...
}

// 使用
const db = bluewater({
    database: { "database-name": "postgres", connection: { ... } },
    sqlDefs: { getList: { method: "select", sql: "..." } }
});
```

#### S5. `funcs_map.json` 编译时绑定

```javascript
// src/util/utils.js
const funcsMap = require("./../../res/json/funcs_map.json");
function getFunctionName(name) {
    return funcsMap[name];  // ← 用户无法扩展
}
```

`&[orderBy]` 标签只能映射到内置的 `funcs_map.json` 中定义的函数。用户想注册自定义 SQL 函数必须直接修改包内的 JSON 文件，这在 `node_modules` 中是不可能的。

**建议**: 支持通过配置传入自定义函数映射：
```javascript
const db = bluewater({
    functions: { myFunc: " CUSTOM_SUFFIX " }
});
```

#### S6. `components/` 语义模糊

当前 `components/` 下只有 `lambda.js`（Query Builder）。"Components" 在软件开发中通常指：
- UI 组件（React/Vue）
- 可插拔的功能模块
- 业务组件

而此处实际是一个 **SQL 查询构建器**，放在 `components/` 下缺乏语义关联。

**建议**: 重命名为 `query-builder/` 或 `builder/`。

#### S7. `test/` 不是测试目录

```javascript
// test/index.js - 这是"试用脚本"，不是测试
require("coralian");
const bluewater = require("../src/index");
const condition = { test: "abc", ... };
bluewater().testLike({ condition, success: (res) => { console.log(res); } });
```

缺少:
- ❌ 测试框架（jest / mocha）
- ❌ 断言（assert / expect）
- ❌ 测试隔离（每个测试独立 environment）
- ❌ Mock / Stub（无法测试数据库不可用时的行为）
- ❌ CI 配置

**建议**: 
```
test/
├── unit/
│   ├── engine.test.js          ← SQL 编译引擎单元测试
│   ├── select-cache.test.js    ← 缓存模块测试
│   └── lambda.test.js          ← Query Builder 测试
├── integration/
│   ├── postgres.test.js        ← PostgreSQL 集成测试

├── fixtures/
│   └── sql-defs.json           ← 测试用 SQL 定义
└── jest.config.js              ← 测试配置
```

#### S8. 缺少错误类型层次结构

```javascript
// 所有错误都是这样抛出的:
function sqlError(msg) { throw new Error(msg || "SQL 错误"); }
```

调用方无法区分"参数缺失"、"SQL 语法错误"、"数据库连接失败"、"不支持的数据库类型"等不同错误类型。

**建议**:
```javascript
// src/errors.js
class BluewaterError extends Error {
    constructor(msg, code) { super(msg); this.code = code; this.name = "BluewaterError"; }
}
class SqlCompileError extends BluewaterError {}    // SQL 编译错误
class DatabaseError extends BluewaterError {}       // 数据库错误
class ParameterError extends BluewaterError {}      // 参数错误
class UnsupportedError extends BluewaterError {}    // 不支持的操作
```

---

#### S9. 模块依赖方向问题

```
util/utils.js
  └── require("../../res/json/funcs_map.json")  ← 工具层依赖具体资源文件
```

依赖方向应该是:
```
资源文件 ← 工具层 ← 业务层
```

但现在是:
```
工具层 → 资源文件
```

这意味着 `util/utils.js` 无法在不加载 `funcs_map.json` 的情况下被单独使用或测试。

**建议**: 将 `getFunctionName` 从 `utils.js` 中分离出来，作为一个可注入的依赖：
```javascript
// utils.js - 纯工具函数，无文件依赖
function chkTagName(name) { ... }
function sqlError(msg) { ... }

// 函数映射单独管理
// adapter/base/engine.js
const funcsMap = require("../../config/funcs-map.json");
function getFunctionName(name) { return funcsMap[name]; }
```
