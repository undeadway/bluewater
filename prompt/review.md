# 任务

扫描 `目录结构` 中定义的内容，对其中的代码进行审查。生成一份用 md 格式编写的代码分析报告。

审查要求如下：
- 分析一下当前整个工程的实现是否合理。
- 和其他数据库中间适配器（有的话）相比，可以打多少分。
- 有哪些加分项，加分都加在了哪里。
- 有哪些扣分项，扣分都扣在了哪里，改进建议是什么。
- 核心运作逻辑是否合理。
- 插件机制是否合理。

最终把审查结果输出到 `@worksapce/prompt/审查结果/` 目录下，命名为 `代码结构审查-YYYYMMDDHHmmss.md` ，YYYYMMDDHHmmss 是日期格式。

## 审查检查清单

执行审查时，请逐项检查以下内容：

### 1. 目录命名与语义
- [ ] 目录名是否准确表达了内容的性质？（如 `parts/`、`components/`、`misc/` 等泛化命名）
- [ ] 是否存在语义重叠的目录？（如两个目录都叫 `archive` 但功能类似）
- [ ] 文件名拼写是否正确？（如 `lamdba.js` → `lambda.js`）
- [ ] 目录层次是否过深？（超过 4 层应警惕）

### 2. 入口文件职责
- [ ] 入口文件（`index.js`）是否承担了过多职责？
- [ ] 配置加载、核心逻辑、事务管理是否混合在同一个文件中？
- [ ] 是否存在 IIFE 级别的副作用（模块加载时立即执行 I/O）？
- [ ] 是否支持多实例创建？还是强制全局单例？

### 3. 模块依赖方向
- [ ] 是否存在反向依赖？（工具层 → 资源文件、底层 → 上层）
- [ ] 是否存在循环依赖？
- [ ] 工具函数是否保持纯函数、无文件依赖？
- [ ] 资源文件（JSON、配置）是否通过注入方式传递，而非硬编码 `require`？

### 4. Dead Code 检查
- [ ] `grep` 搜索项目，确认每个 `export` 的文件都被引用
- [ ] 空实现 / 空方法（仅有 `init() {}` 骨架）是否有存在的必要？
- [ ] TODO 注释是否对应未完成的关键功能？

### 5. 适配器 / 插件机制
- [ ] 适配器接口是否有契约定义（JSDoc / 类型定义）？
- [ ] 新增适配器是否需要修改入口文件？还是仅需添加文件？
- [ ] 是否支持运行时切换适配器（依赖注入 / 策略模式）？
- [ ] 适配器间的代码重复率如何？

### 6. 资源配置
- [ ] 配置文件路径是否硬编码？是否可自定义？
- [ ] 作为 npm 包，使用者是否可以传入配置而非依赖文件系统路径？
- [ ] 内置资源（JSON map、默认配置）是否可被用户扩展/覆盖？

### 7. 测试基础设施
- [ ] 是否有测试框架（jest / mocha / vitest）？
- [ ] 测试文件是真正的"测试"（有断言、有隔离）还是"试用脚本"？
- [ ] 是否有单元测试覆盖核心逻辑？
- [ ] 是否有集成测试覆盖适配器层？
- [ ] 是否有 CI 配置（GitHub Actions / GitLab CI）？

### 8. 错误处理体系
- [ ] 是否使用统一的错误类型层次？
- [ ] 调用方能否精确捕获不同类型的错误？
- [ ] 异步错误是否都被 try/catch 或 .catch() 处理？
- [ ] 回调风格的错误处理中参数名是否一致（`fail` vs `failed`）？

### 9. 工程化基础设施
- [ ] 是否有 `.github/` 目录？（CI、Issue/PR 模板）
- [ ] 是否有 lint 配置？（ESLint、Prettier）
- [ ] 是否有 `.gitignore` 覆盖常见忽略项？
- [ ] 是否有 `CHANGELOG.md` 和 `CONTRIBUTING.md`？
- [ ] `package.json` 中的 `scripts` 是否可执行且正确？

### 10. 全局状态与副作用
- [ ] 模块加载时是否有副作用？（文件读取、网络请求、修改全局对象）
- [ ] 是否依赖 Monkey-patch / 原型修改？（如 `String.prototype`、`Array.has`）
- [ ] 多个实例之间是否会互相影响状态？
